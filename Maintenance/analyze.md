# ANALYZE — statistics for the planner

The query planner never counts rows directly; it **estimates**. To estimate how
many rows a `WHERE` clause will match, how many distinct groups a `GROUP BY`
will produce, or whether an index scan beats a sequential scan, it reads
precomputed **statistics** from the `pg_statistic` catalog (exposed readably as
`pg_stats`). `ANALYZE` is what builds those statistics, from a **random
sample** of the table. Source: `src/backend/commands/analyze.c`.

Stale statistics are a leading cause of bad plans: the planner thinks a
predicate matches 10 rows and picks a nested loop, when it really matches 10
million. Keeping statistics fresh is as important as reclaiming dead tuples —
which is why `ANALYZE` is a first-class maintenance task alongside `VACUUM`.

## The sample size is fixed, not a percentage

This surprises people: `ANALYZE` reads a **fixed number of rows**, not a
fraction of the table. The target is:

```
targrows = 300 * statistics_target
```

With the default `default_statistics_target = 100`, that is **30,000 rows** —
whether the table has 100 thousand rows or 100 billion. (The exact value is the
maximum over all analyzable columns of `300 * attstattarget`, with a floor of
100 rows; `std_typanalyze` sets `minrows = 300 * attstattarget`.)

The consequence: `ANALYZE` cost barely grows with table size, but the sample
becomes a smaller and smaller *fraction* of a huge table. For very large or very
skewed columns you raise the per-column target (below) to compensate.

## Two-stage sampling

Reading 30,000 rows scattered randomly across a billion-row table would mean
30,000 random I/Os. Instead `ANALYZE` samples in two stages:

### Stage 1 — block sampler

Choose which **pages** (blocks) to read, using a uniform random block sampler.
Reading whole pages keeps I/O closer to sequential and far cheaper than chasing
individual rows.

### Stage 2 — reservoir sampling (Vitter's algorithm Z)

As it reads rows from the chosen pages, `ANALYZE` keeps a **reservoir** of
`targrows` rows:

- while the reservoir has room, keep every row;
- once full, each new row *may* replace a random existing one, with a
  probability that **decreases** as more rows are seen.

Vitter's algorithm produces a **uniform** random sample without knowing the
total row count in advance — exactly the situation here, since the planner only
has an estimate of how many rows the chosen blocks hold. Every row that is read
had an equal chance of ending up in the final sample.

## What gets computed, per column

From the finished sample, `ANALYZE` computes and stores in `pg_statistic`:

| Statistic | Meaning | Used for |
|-----------|---------|----------|
| `null_frac` | fraction of NULLs | `IS NULL` selectivity, join sizing |
| `avg_width` | average value width in bytes | memory / cost estimates |
| `n_distinct` | number of distinct values (or a negative ratio for "scales with table") | `GROUP BY` and `DISTINCT` sizing, join selectivity |
| **MCV** | **most common values** and their frequencies | equality selectivity for skewed data |
| **histogram** | equal-frequency bucket boundaries over the non-MCV values | range selectivity (`<`, `>`, `BETWEEN`) |
| `correlation` | correlation between physical row order and logical value order | index-scan vs. bitmap-scan cost |

The MCV list and the histogram are complementary: the MCV list captures
**skew** (a few values that dominate), and the histogram captures the
**spread** of everything else. Both lists hold up to `statistics_target`
entries — raising the target makes both more detailed.

### Reading them back

```sql
SELECT attname, null_frac, n_distinct,
       most_common_vals, most_common_freqs,
       histogram_bounds, correlation
FROM   pg_stats
WHERE  tablename = 'accounts';
```

## How the planner uses them

- `WHERE status = 'active'` — look `'active'` up in the MCV list; if present, use
  its stored frequency directly. If not, assume it is rarer than the least
  common MCV.
- `WHERE created < '2024-01-01'` — sum the histogram buckets below the bound.
- `GROUP BY customer_id` — use `n_distinct` to estimate the number of groups.
- index scan vs. bitmap heap scan — use `correlation`: a highly correlated
  column (e.g. an append-only timestamp) makes a plain index scan cheap because
  matching rows are physically clustered.

## Extended statistics (multi-column)

Per-column statistics assume columns are **independent**. When they are not —
`city` and `postal_code`, say — the planner multiplies selectivities and badly
underestimates. `CREATE STATISTICS` builds **extended statistics** capturing
functional dependencies, multi-column n-distinct, and multi-column MCVs:

```sql
CREATE STATISTICS s_city_zip (dependencies, ndistinct, mcv)
    ON city, postal_code FROM addresses;
ANALYZE addresses;    -- extended stats are gathered by ANALYZE too
```

Source: `src/backend/statistics/`.

## Tuning the sample: `statistics_target`

```sql
-- global default (affects newly analyzed tables)
SET default_statistics_target = 200;              -- session
ALTER SYSTEM SET default_statistics_target = 200; -- cluster

-- per column (the usual, surgical approach)
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
ANALYZE orders;      -- re-sample with the new target
```

Trade-off: a higher target → larger sample → more MCV/histogram entries →
better estimates for skewed or large columns, but a **slower** `ANALYZE` and a
larger `pg_statistic`. Raise it selectively on the columns that drive bad plans,
not globally.

## When ANALYZE runs

- **Autovacuum** runs it automatically when enough rows have changed — the
  threshold is `analyze_threshold + analyze_scale_factor * reltuples`, tracked
  via `mod_since_analyze` (inserts + updates + deletes since the last analyze).
  See [autovacuum.md](autovacuum.md) and [parameters.md](parameters.md).
- **Manually**, when you need fresh stats immediately — after a bulk load, a
  big data change, or creating/altering `STATISTICS`:

```sql
ANALYZE;                       -- whole database
ANALYZE accounts;              -- one table
ANALYZE accounts (balance);    -- specific columns
ANALYZE (VERBOSE) accounts;    -- print what it sampled
VACUUM (ANALYZE) accounts;     -- do both in one pass
```

A bulk `COPY` or `INSERT ... SELECT` into an empty table leaves `pg_statistic`
empty until something analyzes it. Always `ANALYZE` after a large load rather
than waiting for autovacuum, or the first queries may get terrible plans.
