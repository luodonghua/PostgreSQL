# Autovacuum — who vacuums what, and when

You almost never run `VACUUM` or `ANALYZE` by hand. The **autovacuum** subsystem
does it continuously in the background. The interesting question — and the one
most people get wrong — is *how it decides which of the many tables across many
databases to work on next*. This document walks through that decision, grounded
in `src/backend/postmaster/autovacuum.c`.

Two levels of selection happen:

1. The **launcher** picks a **database**.
2. A **worker** connected to that database picks the **tables** that are over
   threshold, and processes them in priority order.

## The process model

- One **autovacuum launcher** runs for the whole cluster. It wakes up every
  `autovacuum_naptime` (default **60 s**). That naptime is **divided among the
  databases**, so in a cluster with *N* active databases the launcher starts a
  worker roughly every `naptime / N` seconds.
- On each wakeup it starts **at most one worker**, after choosing a database.
- Up to `autovacuum_max_workers` (default **3**) workers run **concurrently**,
  possibly in different databases.
- Workers share a single I/O budget: the cost-based delay is **balanced across
  active workers**, so adding workers does not multiply the disk impact (see
  [parameters.md](parameters.md#cost-based-delay)).

Autovacuum must be enabled (`autovacuum = on`, the default) *and* the stats
collector must be running (`track_counts = on`). Even with
`autovacuum = off`, the launcher still forces **anti-wraparound** vacuums —
that safety net cannot be switched off.

## Picking a database (the launcher)

![Autovacuum launcher and database selection](animations/autovacuum_db.gif)

The launcher chooses a database by priority; XID-wraparound danger overrides
everything. (Generated by
[`animations/make_autovacuum_db_gif.py`](animations/make_autovacuum_db_gif.py).)

From `do_start_worker()`, the launcher chooses in this order:

1. **XID wraparound danger.** If **any** database has
   `datfrozenxid` older than `nextXid - autovacuum_freeze_max_age`, pick the
   database with the **oldest `datfrozenxid`** — regardless of when it was last
   processed. Protecting against wraparound wins over everything.
2. **MultiXact wraparound danger.** Otherwise, if any database's `datminmxid`
   is past the multixact limit, pick the one with the **oldest `datminmxid`**.
   (XID danger is considered before MultiXact danger.)
3. **Oldest attention.** Otherwise (the common case), pick the database with the
   **oldest last-autovacuum time** — the one that has waited longest — while:
   - **skipping databases with no stats entry** (nobody has connected since
     stats were initialized, so there is nothing to do), and
   - **skipping databases processed less than one `naptime` ago** (so the
     launcher does not keep re-picking the same database before pgstat has
     recorded that it was just handled).

```sql
-- which databases are closest to a forced wraparound vacuum
SELECT datname, age(datfrozenxid) AS xid_age,
       age(datfrozenxid)::float / current_setting('autovacuum_freeze_max_age')::int
         AS fraction_of_limit
FROM   pg_database
ORDER  BY xid_age DESC;
```

## Picking tables (the worker)

![Autovacuum table selection and scoring](animations/autovacuum_tables.gif)

Each table's dead-tuple count is compared to a size-scaled threshold; tables
over threshold are vacuumed, prioritized by how far past they are. (Generated by
[`animations/make_autovacuum_tables_gif.py`](animations/make_autovacuum_tables_gif.py).)

Once connected, the worker inspects **every** table and materialized view in
the database. For each one, `relation_needs_vacanalyze()` computes three
thresholds and compares them to counters from the cumulative statistics system.

### The thresholds

```
vacuum threshold  = autovacuum_vacuum_threshold
                  + autovacuum_vacuum_scale_factor   * reltuples
                  (clamped to autovacuum_vacuum_max_threshold, if set)

insert threshold  = autovacuum_vacuum_insert_threshold
                  + autovacuum_vacuum_insert_scale_factor * reltuples * pct_unfrozen

analyze threshold = autovacuum_analyze_threshold
                  + autovacuum_analyze_scale_factor  * reltuples
```

### The decision

| Condition | Action |
|-----------|--------|
| `n_dead_tup > vacuum threshold` | **vacuum** the table |
| `n_ins_since_vacuum > insert threshold` | **vacuum** (insert-driven; freezes pages, helps index-only scans) |
| `n_mod_since_analyze > analyze threshold` | **analyze** the table |
| `age(relfrozenxid) > autovacuum_freeze_max_age` *(or `relminmxid` past its limit)* | **forced anti-wraparound vacuum** |

`n_dead_tup`, `n_ins_since_vacuum`, and `n_mod_since_analyze` all come from
`pg_stat_all_tables`, so you can reproduce the decision yourself:

```sql
SELECT relname, n_dead_tup, n_mod_since_analyze, n_ins_since_vacuum,
       last_autovacuum, last_autoanalyze
FROM   pg_stat_all_tables
ORDER  BY n_dead_tup DESC
LIMIT  20;
```

### Why the scale factor matters

Because the threshold scales with `reltuples`, **big tables tolerate
proportionally more dead tuples before being vacuumed**. With the default
`scale_factor = 0.2`, a 100-million-row table waits for ~20 million dead tuples
before autovacuum fires — often far too much bloat. The standard fix is to
**lower the scale factor** (or set a `vacuum_max_threshold` cap) for large,
busy tables; see [parameters.md](parameters.md#large-busy-tables).

The insert threshold uses `pct_unfrozen` (derived from `relallfrozen`), so an
insert-only table is judged by inserts into its still-active, unfrozen portion —
this is what drives the periodic freezing of append-only tables.

### Prioritizing: scores

Several tables can be due at once, but workers are limited. Recent PostgreSQL
(v19 / 20devel) assigns each table a **score** = the worst of its component
ratios `value / threshold`, so a table 4× past its threshold outranks one just
barely over. The components are the vacuum, insert-vacuum, analyze, XID-age, and
MultiXact-age ratios, each multiplied by a tunable weight:

```
autovacuum_vacuum_score_weight
autovacuum_vacuum_insert_score_weight
autovacuum_analyze_score_weight
autovacuum_freeze_score_weight
autovacuum_multixact_freeze_score_weight
```

(Each defaults to `1.0`, range `0.0`–`10.0`.) Tables that have passed the
**failsafe** age get their freeze score scaled up aggressively so they sort to
the very front. Setting **all** weights to `0.0` restores the older
pre-v19 ordering, in which anti-wraparound tables came first and the rest were
unordered.

> Version note: the per-component **score weight** GUCs and
> `autovacuum_vacuum_max_threshold` are new in the PostgreSQL master branch
> (20devel) this repository is built against. The threshold formulas,
> launcher/worker model, and anti-wraparound behavior apply to all supported
> versions.

## What a worker does to a chosen table

For each table it decided to process, the worker runs the same lazy vacuum
and/or analyze described in [vacuum.md](vacuum.md) and [analyze.md](analyze.md),
subject to the **cost-based delay** so background maintenance does not saturate
disk I/O. If a table is a wraparound case, the vacuum is marked
`is_wraparound` and will **wait for locks** rather than skip the table.

## Per-table overrides

Any of the thresholds can be overridden per table with storage parameters —
essential for mixing a few huge hot tables with many small ones:

```sql
-- vacuum this big table far more eagerly than the global default
ALTER TABLE events SET (
    autovacuum_vacuum_scale_factor  = 0.01,
    autovacuum_vacuum_threshold     = 10000,
    autovacuum_analyze_scale_factor = 0.005
);

-- disable autovacuum for a staging table (anti-wraparound still applies!)
ALTER TABLE staging SET (autovacuum_enabled = false);
```

## Monitoring autovacuum

```sql
-- is autovacuum currently working, and on what?
SELECT pid, datname, relid::regclass, phase,
       heap_blks_scanned, heap_blks_total, num_dead_item_ids
FROM   pg_stat_progress_vacuum;

-- recent autovacuum/analyze activity per table
SELECT relname, autovacuum_count, autoanalyze_count,
       last_autovacuum, last_autoanalyze, n_dead_tup
FROM   pg_stat_all_tables
WHERE  last_autovacuum IS NOT NULL
ORDER  BY last_autovacuum DESC;
```

Set `log_autovacuum_min_duration = 0` to log every autovacuum action with its
timing, pages/tuples removed, and whether it was anti-wraparound. See the
detailed playbook in
[`monitor-autovacuum.md`](monitor-autovacuum.md).

## Common failure modes

| Symptom | Likely cause |
|---------|--------------|
| Big table bloats, autovacuum "never" runs on it | default `scale_factor` → threshold enormous; lower it per table |
| `age(relfrozenxid)` keeps climbing | autovacuum can't keep up, or a long transaction / replication slot / prepared xact is **holding back the xmin horizon** so nothing is reclaimable |
| Autovacuum "running forever" | cost-delay too conservative for a huge table; raise `autovacuum_vacuum_cost_limit` or lower the delay |
| Anti-wraparound vacuum stuck | it's waiting on a lock (e.g. a session holding the table); the forced vacuum will not skip it |

Most of these are really **parameter** problems — see
[parameters.md](parameters.md).
