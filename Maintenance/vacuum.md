# VACUUM — reclaiming dead tuples

PostgreSQL uses **MVCC** (Multi-Version Concurrency Control): an `UPDATE` or
`DELETE` never overwrites or erases a row in place. It leaves the old row
version on the page, marked dead, so transactions with an older snapshot can
still see it. Those dead tuples — and the index entries pointing at them —
accumulate as **bloat** until something reclaims them. That something is
`VACUUM`. Source: `src/backend/access/heap/vacuumlazy.c`,
`pruneheap.c`, `visibilitymap.c`, and `src/backend/commands/vacuum.c`.

VACUUM does **not** normally return disk space to the operating system. It
makes dead space reusable *inside* the table (and index) files. (`VACUUM FULL`
rewrites the whole table to shrink it, but takes an `ACCESS EXCLUSIVE` lock and
is a different, heavier operation — covered briefly at the end.)

## What a dead tuple is

```
UPDATE accounts SET balance = balance - 10 WHERE id = 7;
```

This does not change the existing row. It:

1. writes a **new** version of row 7 (new tuple, new `ctid`),
2. marks the **old** version with `xmax` = the updating transaction's XID,
3. adds an index entry for the new version (unless the update is HOT — below).

Once no running or future snapshot can see the old version, it is **dead** and
its space is reclaimable. VACUUM is what detects that and reclaims it.

## The three phases (lazy vacuum)

From the file header of `vacuumlazy.c`, a heap relation is vacuumed in three
phases that behave like states in a state machine:

### Phase I — scan the heap

Walk the heap page by page. On each page VACUUM:

- **Prunes** the page (`heap_page_prune`): dead tuples and dead HOT-chain
  members are removed, and redirect/dead line pointers are compacted. Live
  tuples may be moved to defragment free space within the page.
- **Freezes** tuples that are old enough (see [Freezing](#freezing-and-xid-wraparound)).
- **Records the TID** (page number + line pointer) of each dead tuple that
  still needs its index entries removed, into an in-memory **TID store**.
- Sets the page's **visibility-map** bits if it qualifies (below).

### Phase II — index vacuuming

Now that every dead TID on the scanned pages is known, scan **each index** and
delete the entries that point at those TIDs. This must happen *before* the heap
line pointers are freed — otherwise a freed slot could be reused by a brand-new
row while a stale index entry still pointed at that slot, and a query could
follow the index straight to the wrong row.

Phase II is **skipped** if the table has no indexes, or if VACUUM found very
few dead entries, or if the [wraparound failsafe](#the-failsafe) has fired.
Manual `VACUUM` can process multiple indexes in **parallel**
(`vacuumparallel.c`); autovacuum can too, when configured.

### Phase III — reap the heap

Revisit the pages referenced in the TID store and turn each dead line pointer
into free space, updating the page. The **free-space map (FSM)** is updated so
future `INSERT`/`UPDATE` can reuse the space.

### The TID store can fill mid-scan

The TID store has a memory budget (`maintenance_work_mem`, or
`autovacuum_work_mem` for autovacuum). If it fills up during Phase I, VACUUM
**suspends** Phase I, runs Phases II and III to drain the known dead TIDs, then
**resumes** Phase I where it left off. A table with far more dead tuples than
the memory budget therefore does multiple index passes — one more reason to
give VACUUM enough memory and to not let bloat run away.

Between phases, VACUUM updates the FSM every `VACUUM_FSM_EVERY_PAGES` so
concurrent sessions can start reusing space before the whole table is done.

## Heap-only tuples (HOT) reduce the work

If an `UPDATE` does **not** change any indexed column, and there is room on the
same page, PostgreSQL uses a **HOT update**: the new version lives on the same
page and the old version's line pointer is turned into a redirect to it. No new
index entry is created — all indexes still point at the original line pointer,
which now redirects. This means:

- less index bloat and fewer index writes,
- **HOT pruning** can reclaim intermediate dead versions during ordinary page
  access (even between vacuums), via `heap_page_prune_opt`.

HOT is one of the biggest reasons to keep hot, frequently-updated columns
**out** of indexes. See `src/backend/access/heap/README.HOT`.

## The visibility map (VM)

Each heap page has a two-bit entry in the **visibility map**
(`visibilitymap.c`):

| Bit | Meaning |
|-----|---------|
| `all-visible` | every tuple on the page is visible to all transactions (no dead tuples needing cleanup, nothing in-flight) |
| `all-frozen`  | in addition, every tuple is frozen |

The VM pays off in two ways:

- **Index-only scans** can skip visiting the heap for a row if its page is
  marked all-visible (the index entry alone is trusted).
- **VACUUM can skip pages.** A normal vacuum skips `all-frozen` pages entirely,
  and can skip runs of `all-visible` pages. This is why a mostly-static table
  vacuums almost instantly after the first pass.

There is also a page-level `PD_ALL_VISIBLE` flag kept in sync with the VM bit.

## Normal vs. aggressive vacuum

- A **normal** vacuum skips pages it is allowed to skip (via the VM), for speed.
  It may still *eagerly* scan some `all-visible`-but-not-`all-frozen` pages to
  freeze them, reducing the backlog for the next aggressive vacuum. The number
  of successful eager freezes per run is capped
  (`MAX_EAGER_FREEZE_SUCCESS_RATE`, tunable via
  `vacuum_max_eager_freeze_failure_rate`) so the extra work is amortized.
- An **aggressive** vacuum must scan **every** unfrozen tuple so it can advance
  `relfrozenxid`. It is triggered by age (see below). It cannot skip
  `all-visible` pages, only `all-frozen` ones.

## Freezing and XID wraparound

![Freeze and XID wraparound](animations/freeze.gif)

The circular XID clock, the frozen horizon (`relfrozenxid`), the
`vacuum_freeze_min_age` band, and the `autovacuum_freeze_max_age` danger line.
(Generated by [`animations/make_freeze_gif.py`](animations/make_freeze_gif.py).)

### The problem freezing solves

Each tuple stores the transaction ID (`xmin`) that created it. Transaction IDs
are **32-bit** and compared on a **circular** number line of ~4.2 billion
values. "Older than" effectively means "within the previous ~2 billion XIDs".
As the global XID counter advances, a very old live tuple would eventually fall
on the "future" side of that circle and **appear to vanish** — catastrophic,
silent data loss.

### What freezing does

**Freezing** stamps a sufficiently old live tuple as unconditionally visible,
so its original `xmin` no longer matters. VACUUM freezes tuples and then
advances the table's **`relfrozenxid`** — the oldest XID still unfrozen in that
table. The per-database **`datfrozenxid`** is the minimum over its tables.

Key knobs (details in [parameters.md](parameters.md)):

| GUC | Role |
|-----|------|
| `vacuum_freeze_min_age` | minimum age before a tuple is frozen during a vacuum |
| `vacuum_freeze_table_age` | age of the table that makes the next vacuum **aggressive** |
| `autovacuum_freeze_max_age` | age of `relfrozenxid` that **forces** an anti-wraparound autovacuum |
| `vacuum_multixact_freeze_min_age` / `_table_age` | same idea for MultiXact IDs (row locks / `SELECT FOR SHARE`, etc.) |

MultiXact IDs (used when multiple transactions lock the same row) have their
own 32-bit space and their own freezing, tracked per table as `relminmxid` and
per database as `datminmxid`. Everything below about XID age applies to
MultiXacts in parallel.

### Anti-wraparound vacuum

If a table is never otherwise vacuumed (insert-only, or autovacuum disabled for
it), `relfrozenxid` falls behind. When
`age(relfrozenxid) ≥ autovacuum_freeze_max_age`, autovacuum launches a
**forced anti-wraparound** vacuum on that table — **even if autovacuum is
disabled for the table**. This is not optional; it protects your data. (It can
be `SKIP_LOCKED`-exempt and will wait for locks, which is why a long-held lock
on a big table can be dangerous.)

### The failsafe

If age climbs dangerously high anyway (`vacuum_failsafe_age`,
`vacuum_multixact_failsafe_age`), VACUUM enters a **failsafe** mode: it stops
the cost-based delay and **skips index vacuuming (Phases II/III)** to freeze the
heap as fast as possible. The goal shifts entirely to advancing `relfrozenxid`
before wraparound.

### Monitoring

```sql
-- per-table XID age (how close to needing anti-wraparound vacuum)
SELECT relname, age(relfrozenxid) AS xid_age
FROM   pg_class
WHERE  relkind IN ('r','m','t')
ORDER  BY xid_age DESC
LIMIT  20;

-- per-database age vs autovacuum_freeze_max_age
SELECT datname, age(datfrozenxid) AS xid_age
FROM   pg_database
ORDER  BY xid_age DESC;
```

See also [`monitor-autovacuum.md`](monitor-autovacuum.md).

## Finishing up: truncation and statistics

After the three phases, if whole pages at the **end** of the table are now
empty, VACUUM can **truncate** them and return that space to the OS. This needs
a brief `ACCESS EXCLUSIVE` lock and can be disabled per table
(`vacuum_truncate` / the `TRUNCATE` option).

Finally VACUUM updates `pg_class` (`relpages`, `reltuples`, `relallvisible`,
`relallfrozen`, `relfrozenxid`) and the cumulative statistics so the **planner**
has fresh row counts and **autovacuum** sees up-to-date dead-tuple numbers.

## VACUUM vs. VACUUM FULL

| | `VACUUM` (lazy) | `VACUUM FULL` |
|---|---|---|
| Lock | `SHARE UPDATE EXCLUSIVE` (reads/writes continue) | `ACCESS EXCLUSIVE` (blocks everything) |
| Space to OS | only trailing empty pages | yes — rewrites the whole table compactly |
| Extra disk | none | needs room for a full copy |
| Use when | routine, continuous | one-off, severe bloat, maintenance window |

For online bloat removal without a full-table lock, prefer
`pg_repack`/`pg_squeeze` — see
[`postgresql-maintenance.md`](postgresql-maintenance.md).

## Running it manually

```sql
VACUUM;                       -- whole database, no analyze
VACUUM (VERBOSE) accounts;    -- one table, print a per-phase report
VACUUM (ANALYZE) accounts;    -- vacuum then refresh statistics
VACUUM (FREEZE) accounts;     -- freeze everything eligible now
VACUUM (DISABLE_PAGE_SKIPPING) accounts;  -- scan every page (recovery/debug)
```

In practice you rarely run `VACUUM` by hand — **autovacuum** does it for you.
How autovacuum decides *which* tables and databases to process, and when, is in
[autovacuum.md](autovacuum.md). The knobs that control all of this are in
[parameters.md](parameters.md).
