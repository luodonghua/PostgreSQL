# Hybrid JSONB + relational design (banking example)

A worked example showing *why* you should keep frequently-updated fields in a
small, dedicated relational row and reserve JSONB for complex, rarely-changed
data. The real driver, verified by a controlled test, is the **size of the row
each `UPDATE` rewrites** — not whether a field is a column or a JSONB key.
All numbers below were measured on PostgreSQL 18.6.

Runnable script: [hybrid-jsonb-banking.sql](hybrid-jsonb-banking.sql)

## The performance problem with JSONB

PostgreSQL cannot update a JSONB document *in place*. Changing a single key
with `jsonb_set(...)` produces an entirely new JSONB value. Because of MVCC,
the `UPDATE` then writes a **brand-new copy of the whole row**, and that new
tuple is written to the WAL (Write-Ahead Log) in full.

So the WAL and table-bloat cost of an update is driven by the size of the
**entire row being rewritten**, not by how many bytes you logically changed.

In banking, the account **balance** changes on every debit and credit — it is
the hottest field in the system. The customer **profile / KYC** data (name,
documents, preferences) is large but changes rarely. If balance lives inside
the same JSONB blob as the profile, every transaction rewrites ~1 KB of
untouched profile data.

## The design

| Table | Contents | Update frequency | Row size |
|-------|----------|------------------|----------|
| `accounts` | identity + big `profile` JSONB (customer, KYC, prefs) | rare | ~1 KB |
| `account_balances` | `balance`, `status`, `updated_at` | every transaction | ~56 B |

The hot field is split into its own **narrow row**, linked by `account_id`.
The large JSONB blob is never touched by a balance update.

For contrast the script also builds a **bad** table, `accounts_jsonb_only`,
where `balance` and `status` are buried inside the big JSONB document.

## Verified results (PostgreSQL 18.6)

Average tuple size an `UPDATE` must rewrite:

| Design | Tuple rewritten per update |
|--------|----------------------------|
| Good — `account_balances` row | **56 bytes** |
| Bad — `accounts_jsonb_only.doc` | **1048 bytes** |

WAL generated by the *same* workload — `balance = balance + 1` across all
5000 accounts, repeated 5 times (25,000 row updates), after a `CHECKPOINT`:

| Design | WAL generated |
|--------|---------------|
| Good — hybrid (relational balance in its own narrow row) | **6.3 MB** |
| Bad — balance inside the big JSONB row | **38 MB** |

Keeping the hot field in its own narrow row cut WAL by roughly **6×** for the
identical business operation. Less WAL means less I/O, smaller/faster
replication streams, less backup volume, and far less table bloat.

### What actually causes the win — a controlled, apple-to-apple test

It is tempting to conclude "a column beats a JSONB key." That is **not** the
real cause. A controlled test isolates the true variable — **row size** — by
holding the profile payload identical and changing only where `balance` lives:

| Design | Avg row size | WAL (5 rounds, isolated, FPI-warmed) |
|--------|--------------|--------------------------------------|
| T1 — balance is a **column**, in the same big ~680 B row | 681 B | **21 MB** |
| T2 — balance is a **JSONB key**, in the same big ~680 B row | 697 B | **21 MB** |
| T3 — balance in its **own narrow 37 B row** | 37 B | **~4–5 MB** |

Reproduced across 3 runs: **T1 ≈ T2** (column vs JSONB key makes almost no
difference when the row is the same size), while **T3 is ~4–5× cheaper**.

**Conclusion:** the lever is not "column vs JSONB" — it is the **size of the row
that each `UPDATE` must write a new MVCC version of**. MVCC rewrites the whole
tuple regardless of which field changed, so a balance update on a ~680 B row
costs the same whether balance is a column or a JSONB key *in that same row*.
The hybrid design wins because it puts the hot field in its **own small row**,
so each update rewrites ~37 B instead of ~680 B. Burying balance in a large
JSONB document is bad precisely because it forces the hot field to live in a
large row.

### Measurement method

```sql
CHECKPOINT;                                   -- avoid first-touch full-page images skewing the result
UPDATE ... ;                                  -- one warm-up update so the measured rounds exclude the FPI
SELECT pg_current_wal_lsn() AS before \gset
-- ... run the measured updates ...
SELECT pg_current_wal_lsn() AS after  \gset
SELECT pg_size_pretty(pg_wal_lsn_diff(:'after', :'before'));
```

> Note: measure *after* a `CHECKPOINT` **and** a warm-up update. The first update
> to a page after a checkpoint logs a full-page image (~8 KB/page), which
> inflates and distorts a one-shot measurement. Repeating the update several
> times, past the warm-up, gives a representative figure.

## You keep the JSONB flexibility

The stable data stays in JSONB, so you still get schema flexibility and can
query inside it with a GIN index. Verified plan:

```sql
SET enable_seqscan = off;
EXPLAIN (ANALYZE)
SELECT count(*) FROM accounts
WHERE profile @> '{"preferences": {"marketing_opt_in": true}}';
```

```
Bitmap Heap Scan on accounts
  Recheck Cond: (profile @> '{"preferences": {"marketing_opt_in": true}}')
  ->  Bitmap Index Scan on idx_accounts_profile
        Index Cond: (profile @> '{"preferences": {"marketing_opt_in": true}}')
```

A typical read joins the hot balance to the stable profile:

```sql
SELECT a.account_no, b.balance, b.status,
       a.profile->'customer'->>'name' AS name
FROM accounts a
JOIN account_balances b USING (account_id)
WHERE a.account_no = 'ACC00000042';
```

## Takeaway

- **The real lever is row size, not column-vs-JSONB.** MVCC rewrites the whole
  tuple on every `UPDATE`, so keep the *row* that holds a hot field small. A
  balance update costs the same whether balance is a column or a JSONB key *in
  the same big row* (measured: 21 MB vs 21 MB); it only gets cheap when balance
  lives in its **own narrow row** (~4–5 MB).
- **Hot, high-write fields → their own narrow relational row** (balance, status,
  counters, timestamps). Small tuples → cheap WAL, cheap updates, less bloat.
- **Complex, read-mostly, schema-flexible data → JSONB** (profile, KYC,
  preferences). Indexed with GIN for containment queries.
- Never trap a hot field inside a large row — whether that bulk is a big JSONB
  document or just many wide columns.
