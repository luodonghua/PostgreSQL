# Hash — equality-only index

A Hash index maps a column value's **hash code** to a bucket, giving fast
**equality** (`=`) lookups. It supports *only* `=` — no ranges, no ordering. It
is crash-safe and WAL-logged (since PostgreSQL 10). Source:
`src/backend/access/hash/`.

## When to use it

- Equality on a single column where you never need ranges or ordering:
  `WHERE col = :value`
- Especially when the key is **large** (long text, big values): a hash index
  stores only the 4-byte hash code, not the value, so it can be much smaller
  than a B-tree on the same column.

```sql
CREATE INDEX idx_token ON sessions USING hash (token);
SELECT * FROM sessions WHERE token = :t;      -- uses the hash index
SELECT * FROM sessions WHERE token < :t;      -- CANNOT use it (no ranges)
```

In practice B-tree is often preferred even for equality, because it also serves
ranges/ordering and supports unique constraints. Choose Hash when the key is
large and the workload is purely equality.

## Core idea: value → hash code → bucket

```
value  ──hash()──►  hash code  ──mod N buckets──►  bucket number
'alice@example.com'    0x9f3c…        bucket 2

   bucket 0   bucket 1   bucket 2   bucket 3
  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
  │ codes… │ │ codes… │ │ 0x9f3c │ │ codes… │   each entry = (hash code, ctid)
  └────────┘ └────────┘ └───┬────┘ └────────┘
                            │ overflow if full
                        ┌───┴────┐
                        │overflow│  (doubly-linked to the bucket page)
                        └────────┘
```

A lookup hashes the query value, finds the bucket, and scans that bucket's pages
for entries with a matching hash code; because hash codes within a page are
**sorted**, the scan uses binary search within a page. Since only the hash code
is stored (not the value), a final **recheck against the heap tuple** confirms
the real value (hash collisions are possible).

## Physical structure: four page types

```
block 0        buckets grow in power-of-2 groups       freed overflow tracking
┌──────────┐   ┌───────┐ ┌───────┐ ┌───────┐ ┌──────────┐ ┌──────────┐
│ METAPAGE │   │bucket0│ │bucket1│ │bucket2│ │ overflow │ │ BITMAP   │
│ bucket   │   │ page  │ │ page  │ │ page  │ │ page     │ │ page     │
│ count,   │   └───────┘ └───────┘ └───┬───┘ └──────────┘ └──────────┘
│ spares[] │                           │  chained (doubly-linked list)
└──────────┘                           └──▶ overflow page ──▶ …
```

1. **Metapage** (block 0) — bucket count, `hashm_spares[]` (overflow accounting),
   and the current split point.
2. **Primary bucket pages** — one permanent first page per bucket.
3. **Overflow pages** — added when a bucket overflows; chained to the bucket in a
   doubly-linked list via the page special space.
4. **Bitmap pages** — track which overflow pages are free for reuse (overflow
   pages can be recycled; they are never returned to the OS).

Entries store only `(hash code, ctid)` — not the indexed value.

## Incremental growth: bucket splits

The index grows **one bucket at a time**, not by a full rebuild. When the index
needs more capacity, a new bucket is added and exactly **one existing bucket is
split**: its tuples are redistributed between the old and new bucket using one
more bit of the hash code.

```
Before split (1 bit of hash):          After adding a bucket (2 bits):
  bucket 0 : hashes ending …0            bucket 0 : …00
  bucket 1 : hashes ending …1            bucket 1 : …01
                                         bucket 2 : …10   ← new; took half of bucket 0
                                         (bucket 0 keeps …00)
```

Bucket pages are allocated in power-of-2 "splitpoint" groups; to avoid a huge
one-shot allocation, large groups are allocated in **four phases**. The physical
block number of any bucket is computed arithmetically from the bucket number plus
`hashm_spares[]`, so primary bucket pages never have to move once created.

There is no shrink: fewer buckets or returning space to the OS requires
`REINDEX`.

## Concurrency

Hash uses buffer content locks, pins, and **cleanup locks**. A cleanup lock on a
primary bucket page (exclusive lock + sole pin) grants the right to reorganize
the whole bucket — used by bucket splits and VACUUM. Splits are performed so that
concurrent scans and inserts can proceed, and the operation is WAL-logged for
crash recovery.

## Trade-offs

| Strength | Weakness |
|----------|----------|
| O(1)-ish equality lookups | **Equality only** — no ranges, no `ORDER BY`, no `MIN`/`MAX` |
| Stores only the hash code → small for large keys | Needs a heap recheck (hash collisions) |
| Grows incrementally (bucket-at-a-time splits) | No unique constraints; cannot shrink without `REINDEX` |
| WAL-logged / crash-safe since PG 10 | B-tree usually preferred unless the key is large |
